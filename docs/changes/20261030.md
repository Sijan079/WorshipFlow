# 2026-10-30: event colours

Asked for by the owner: events should be able to show in a colour on the calendar. Each entry gives the
document, the version before (From), and the version after (To), with the reason.

## 1. An event has a calendar colour

Reason: with several events in a day, colour lets the team tell kinds of event apart at a glance.

### Data-Model.md
From: `ChurchEvent` has no colour.
To: `ChurchEvent.color`, text, not null, default `DEFAULT`. It is one of a fixed set of names (`DEFAULT` (shown as
Blue), `PURPLE`, `GREEN`, `ORANGE`, `RED`, `PINK`, `TEAL`, `GRAY`) held in
`src/features/events/event-colors.ts`, and validated on create and edit. It belongs to the event, so every date of
a repeating event shares it. Not applied to the core doc yet; update it once this is accepted as permanent.

### Database (additive)
One column, `ChurchEvent.color` (migration `prisma/migrations-current/20261031000000_event_color`), applied to the
hosted database before the code, on the owner's approval. Every existing event holds `DEFAULT`, so nothing looks
different until a colour is chosen.

**What went wrong, and the rule it leaves.** The migration was first applied by hand with `prisma db execute`, which
runs the SQL but does not record it in `_prisma_migrations`. The Vercel build runs `prisma migrate deploy` against the
production database on every deploy (`scripts/vercel-build.mjs`; the local dev database is that same hosted
database). It saw the migration as pending, ran it again, and failed with "column color already exists". That failed
the first deploy of this change (`db_migration_failed`), left the previous deployment live, and left a failed row that
blocks every later deploy until it is resolved. It was recovered with
`prisma migrate resolve --applied 20261031000000_event_color`, which closed the failed row and recorded the
migration. (An earlier line in this entry wrongly said `prisma migrate status` does not read `migrations-current`;
it does, and it counts 40 migrations.) **From now on, apply migrations to the hosted database with
`prisma migrate deploy`**, as the build does. If one is ever applied by hand, run `prisma migrate resolve --applied
<name>` straight afterwards, before pushing.

### Screen
- A Color row of named swatches in the New event and Edit event forms. Each swatch has a name and a tick when
  chosen, so colour is never the only clue.
- Calendar chips use the event's colour. A cancelled date stays grey and struck through whatever its colour. An
  overlap is still flagged by the word "Overlap" before the title, so colour no longer doubles as the overlap
  warning.
- List rows and the details card show a small dot in the event's colour.

### Design tokens (needs the owner's review)
`tokens.css` gains `--event-<name>-bg`, `--event-<name>-ink` and `--event-<name>-dot` for all eight colours. The text
on every chip is at least 4.5 to 1 against its background (a test checks this). Blue is a true blue tint
(`--event-blue-*`). It first reused the pale grey panel colour, which was almost the same as the selected day's
background, so a blue chip on the selected day seemed to have no colour (fixed 2026-10-30). Every coloured chip also
has a thin outline in its own text colour, so it holds its shape on any background.

`DESIGN.md` was not changed. A categorical colour palette is a new design element, so it should go through a
grilling session before `DESIGN.md` and `tokens.css` are declared aligned.

## 2. A headcount can be recorded on any date that has happened

Reason: the headcount was only entered inside Mark done, which exists for one-time events. The dates of a repeating
event had a headcount in the data and the API, but no way to set it from the screen. `Product.md` already says events
have an optional per-occurrence headcount.

### Screen
An Attendance icon in the event card's icon row ("Record attendance", or "Edit attendance" once a number exists). It
opens a small inline form, "How many attended (Optional)". An empty box clears the number. It is available for any
date that has started and is not cancelled, repeating or not, done or not. "After the event" still appears only once
a number is recorded.

### Server
`PATCH /api/events/occurrences/{id}` refuses a headcount on a date that has not started or is cancelled (409). Clearing
a headcount is always allowed. Recording a headcount does not mark the date as "Changed".

## 3. Every API response says no-store

Reason: 63 of the 88 API routes (events, people, services, members and others) set no cache header of their own and
relied on framework defaults. Those responses are private, signed-in data, so the intent should be explicit.

### next.config.ts
From: only 25 routes said `Cache-Control: no-store` themselves.
To: a rule on `/api/:path((?!captions/live/).*)` sets `Cache-Control: no-store` on every API response. The public
captions feed (`/api/captions/live/{token}`) is the one exception: it sets its own short caching (`feedCacheControl`)
and carries caption text only.
`src/lib/api-cache-headers.test.ts` checks the rule, and fails if any other route starts choosing its own caching.

### Not changed
Data held in the browser by the data library (1 minute fresh, about 5 minutes kept, in memory per tab) is unchanged.
Pages already said `no-store`. Production was not checked; this was verified on the local dev server.

## 4. Services: newest first, ten per page, with a footer

Reason: the list grows every week and was sorted oldest first, so the newest service was at the bottom.

### Screen
- The newest service is always at the top. The sort is done on the page, so nothing else that reads
  `/api/services` changes.
- Ten services per page, with a footer in the register: "Showing 1 to 10 of 23 services" on the left, and Previous and
  Next arrows around "Page 2 of 3" on the right. The footer stays on a short list, with both arrows off.
- "Select all" covers the rows on the current page only, so a bulk delete never reaches rows the person has not seen.
  Changing a filter goes back to page 1.
- The arrows are quiet icon controls (no border, no fill, muted until hovered, 44px) with a name and tooltip.

### Code
`src/lib/list-pagination.ts` (`paginate`, `latestFirst`, `PAGE_SIZE = 10`, tested) and
`src/components/ui/list-pagination-footer.tsx`, built on `src/components/ui/pagination.tsx`, which is shadcn's
pagination adapted to this app (real buttons, and its light-surface colours, because shadcn's outline button filled
with the dark app background). Events uses the same footer on its list.

## 5. The Events screen now follows the register layout

Reason: Events had its own look. It now follows the page contract in `DESIGN.md` (header, one register with a toolbar,
a footer) like the other list pages, and the owner personalised the details.

### Layout
- Header with `ui-page-header` and the primary New event button. One register surface with a toolbar: the month, the
  previous and next icons, Today, the Month and List switch, and a refresh icon. The count beside the switch was
  removed.
- The details of an event are a separate card beside the calendar, with an X to close it. The calendar goes full
  width whenever the card is closed (the width glides). The card opens when an event, or a day that has events, is
  chosen, or New event is pressed. List view and the past events review list use the same card on a wide screen. On
  a phone the details open under their row, with the purple rule, as Services rows do.
- List and review views have the pagination footer, ten per page, in date order.
- Loading: a calendar-shaped skeleton, shown for the new month while it loads instead of the old month's events
  (the old month is kept underneath only so the page's buttons keep working). Months already loaded appear at once.
- Errors: a red band with Retry, for the month and for the review list. The review list loads on its own after Review
  is pressed; it used to show "Nothing to review" while it loaded, and forever if it failed.
- Past Events to Review: Title Case heading, no count, and a left-arrow icon (named "Back to calendar") instead of a
  labelled button.

### The details card
- The actions are quiet icon buttons under the event's details (no border, no fill, muted, red on hover for the
  destructive ones): Edit, Attendance, Cancel, Announce, Restore, Mark done, Mark not done, Delete. Each has a name
  and a tooltip. One Cancel icon replaces two: with two choices it opens a small menu (Cancel this date, Cancel all
  dates); with one choice it opens that confirmation.
- Cancel this date, Cancel all dates and Delete ask in a modal ("Yes, I am sure"), not inside the card. The icons stay
  on the card behind the modal. Edit and Mark done open inside the card.
- Registration and After the event are shown only when they have something in them. Status shows as a coloured dot and
  a word. Filler lines were removed ("Only the title, date, time and place are shown.", "To delete this event, cancel
  it first.", "Dates are added automatically about four months ahead.", and the explainer in Edit).
- The Repeat choices read Never, Daily and Weekly. Optional labels read "(Optional)" where touched.
- Fields use the shared People field styles. The website switch has no border.

### Motion
The details card slides and fades in and out, the calendar or list glides to its new width, the card content fades
when it changes, the month fades in, list rows fade in one after another, and Edit and Mark done fold open and shut
(the card used to snap shut). Everything follows the system's reduced-motion setting.

## 6. One date picker and one time picker across the app

Reason: the browser's own date and time fields looked different from the Services date picker and from each other.

### Date
Every date field now uses the Services date picker (`ProductionDatePicker`): Events (create and edit), Announcements
(both optional dates, with Clear), and three fields in the service builder. The picker gained a `minValue`, so an end
date cannot be chosen before its start.

### Time
A new `ProductionTimePicker`: an alarm-style popup with three wheels (hour, minute, AM or PM) that scroll up and down
under a highlighted band. It works with a touch scroll, a mouse wheel, a mouse drag, a tap on a row, and the arrow
keys, and keeps the same 24-hour "HH:mm" value the forms always held. Used for Start and End in Events.
`src/lib/time-of-day.ts` holds the tested maths. A test fails if a browser date or time input comes back anywhere.

## 7. Fixes found while checking in the browser

- "Announce this event" opened Announcements with nothing selected after a client navigation: the screen read
  `window.location`, which still has the old address while the new page first renders. It now reads the router.
- Changing the date of a new event now moves the preselected weekday with it, and never undoes a choice made by hand.
- A cancelled date no longer offers "Announce this event".
- The Events screen is tested in an Edge window that Playwright opens (`--browser msedge` in the user's global MCP
  settings), because Opera GX cannot be driven from it.

## 8. Decisions for the owner (nothing here was applied to `DESIGN.md`)

`DESIGN.md` changes go through a grilling session first, so these are recorded as proposals:
1. **Register footer.** `DESIGN.md` does not describe the footer, the pagination control or the quiet icon arrows.
2. **Icon-only actions.** `DESIGN.md` says icons support words and do not replace them. The owner asked for icon-only
   actions in the event card, each with a name and tooltip.
3. **"Keep it".** Serious confirmations read "Yes, I am sure" as `DESIGN.md` says, but the way out reads "Keep it", in
   plain text with no fill, instead of "Cancel", because "Cancel" next to "Cancel this date?" is confusing.
4. **Categorical colours** (item 1) and the **alarm-style time picker** (item 6) are new design elements.
5. **Overlap.** An overlapping event keeps its own colour and is flagged only by the word "Overlap" before its title.
   It used to turn amber.

# Later the same day: the Page Builder becomes a WordPress-style block editor

Asked for by the owner, decided in a grilling session on 2026-10-30 (Q1 to Q20, every recommended answer accepted
except Q6, where the owner asked for WebP). Each entry gives the document, the version before (From), and the
version after (To), with the reason. **The core docs are not changed yet**: they change once the owner accepts this
as permanent.

Method: we study how WordPress and its block editor (Gutenberg) behave and write our own code. No WordPress code is
copied, because WordPress is GPL.

## 9. A block editor, many pages, a menu

Reason: the owner wants the public site to be built the way WordPress pages are built.

### Product.md (Page Builder)
From: "Pages are ordered lists of typed blocks: heading, rich text, image, button, announcements list, events list,
service times, contact." and "A default home page template ships with it."
To: pages are edited in a stack-of-blocks editor. Text is typed directly on the page; other blocks open a settings
panel (a bottom sheet on phones). Autosave every few seconds, undo and redo in the session, Preview with phone,
tablet and desktop widths. A church has many pages (at most 20, with at most 60 blocks each) and a header menu built
from its published pages in an order the church sets. A page's address comes from its title; the first page is the
home page and cannot be deleted. Other pages can be unpublished at any time and deleted only as drafts, with "Yes, I
am sure". Each page has an optional search description (default: its first paragraph). A new church starts with a
ready-made home page that is an ordinary, editable page.

### Roadmap.md (step 8) and the Scope guard in AGENTS.md
From: "a free-form page builder" is deferred.
To: the WordPress-style block editor above is in scope. Still deferred: columns and nested blocks, galleries, video,
embeds, revision history, and Articles (blog posts, a separate step after the editor), plus the old "free-form or
custom-code builder" meaning (no raw HTML, CSS or JavaScript).

## 10. Blocks in version one

### Data-Model.md (`SiteBlockType`)
From: HEADING, RICH_TEXT, ANNOUNCEMENTS_LIST, EVENTS_LIST, SERVICE_TIMES, CONTACT.
To: PARAGRAPH, HEADING, LIST, QUOTE, IMAGE, BUTTON, SPACER, ANNOUNCEMENTS_LIST, EVENTS_LIST, SERVICE_TIMES, CONTACT.
`RICH_TEXT` is replaced by `PARAGRAPH` (nothing is stored under it yet).
Options are only left or centre alignment (text, image, button) and normal or large text. No per-block colours.
Links (buttons and text) may point to another page of the site, an outside address, a phone number or an email
address; only `http`, `https`, `tel` and `mailto` are allowed, and outside links open in a new tab.
Content stays structured JSON per block, never HTML; text styling is a small allowed set (bold, italic, link).

## 11. Images

### Data-Model.md and Architecture.md
From: "Image blocks reference files in Supabase Storage and count toward the workspace storage meter."
To: unchanged, plus: an upload is converted to WebP (quality about 80), shrunk to at most 1600 px wide, and limited
to 10 MB before conversion. Every image needs a short description (alt text).

## 12. The look

### Data-Model.md (`SiteSettings`)
From: "logo, color and font preset, contact details."
To: a logo, one of 5 colour presets and one of 2 font presets (a plain sans and a classic serif). No free colour
pickers. The neutral default look (white page, dark text, soft lavender panels) is used until a preset is chosen.

## 13. Who can edit

### Access-and-Privacy.md
From: "Site management (pages, posts, publish) is a module with its own actions (VIEW, CREATE, EDIT, DELETE, PUBLISH)."
To: unchanged. Owner and Admin can always edit and publish. A Member needs the SITE grant: Edit changes drafts,
Publish goes live. Editing a published page sends it back to Draft for anyone without Publish, the same rule as
announcements. If a second person opens a page someone else is editing, they see "Someone else is editing this
page" and get a view-only page (no live co-editing).

## 14. Built so far (not a contract change)

Everything below is committed on `wip/pre-design-trial`, tested (`npm test`), and was tried in the browser.

- **Database** (migrations applied to the shared database on 2026-10-30): `SiteSettings`, `SitePage`, `SitePageBlock`, the
  SITE module value, the block types of item 10, `SiteImage`, and two lock columns on `SitePage`.
- **Public site** `/c/{church}` and `/c/{church}/{page}`: every published, public page, a menu bar (home first, then the
  church's order), a tab title and search description per page, `noindex` unless the church turned indexing on.
  `/c/{church}/home` redirects to `/c/{church}`; the page address `image` is reserved. Reads go through one narrow data
  layer (`src/features/site/public/public-site-data.ts`), checked by a privacy test. A repeating event is listed once, on
  its next date. Service times are plain text lines, so no service or assignment data is read.
- **Page API** `/api/site/pages`: list, create, edit, publish, delete, with the Site permission, the publish rule shared
  with announcements, draft-only delete, and the home page protected. `/api/site/settings` holds the church address,
  phone and email and the search-engine switch (Publish permission).
- **Editor** (menu item "Page Builder"): add, move and delete blocks, undo and redo, autosave after two seconds when the
  page is valid, Publish and Unpublish, Delete with "Yes, I am sure", **Preview** with phone, tablet and computer
  widths, and **one editor at a time** (a claim renewed every 20 seconds that expires after a minute; a second person
  gets a view-only page, and a save over someone else's claim is refused).
- **Pictures**: uploaded straight from a Picture block, turned into a WebP at most 1600 px wide (JPG, PNG or WebP in, up
  to 10 MB, no SVG, camera details removed), stored in private storage, at most 200 per church. A page can only use the
  church's own pictures. The public picture address answers only while a published, public page uses it, and may be
  remembered for five minutes.
- **Dependency**: `sharp` is now declared in `package.json`.

**Differences from the plan, for the owner:**
- Block settings are shown on the page, beside the block, on every screen size. There is no bottom sheet, because
  `DESIGN.md` says phones have no bottom sheets. Adding one needs a `DESIGN.md` grilling session first.
- Text in a paragraph is plain for now. Bold, italic and links inside text are supported by the stored format and by the
  public page, but the editor does not offer them yet.
- The logo and the colour and font presets (item 12) are not built yet.
- There is no storage meter yet; each picture's size is recorded so one can be added.

## 15. Open for the owner

- Accept items 9 to 13 as permanent so the core docs can be updated.
- The public site's own look is still the neutral default; the real presets still need design.

## 16. Layout blocks and page widths (grilling round of 2026-10-30, Q1 to Q3, Q7 to Q10, Q12)

Reason: the first homepage built with the editor looked plain. A study of two live WordPress pages with REA
(`docs/design/wordpress-layout-study.md`) showed that WordPress pages look designed because of three widths and blocks
that hold other blocks. This reverses the deferral in item 9 ("columns and nested blocks ... still deferred").

### Product.md (Page Builder) and Roadmap.md (step 8)
From: blocks stack in one narrow column; columns, nested blocks, a hero and bands are deferred.
To: the editor gets layout blocks, built in this order, each usable on its own: **(1) widths and the Section block,
(2) the Cover (hero) block, (3) Columns, (4) the site header, footer and look** (item 17).

- **Widths.** Content 720 px (reading), wide 1200 px, full (the whole screen). A block is content width by default.
  Text blocks (Text, Heading, List, Quote) always stay at content width. Only Section, Cover, Columns, Picture and
  Space can be wide or full. Existing pages do not change.
- **Nesting.** A Section holds any normal blocks and one or more Columns blocks. A Column holds normal blocks only. No
  Section inside a Section, no Columns inside Columns: at most three levels.
- **Section.** A full-width band. Background: none, tinted, dark, accent, or a picture with a dark overlay in 3
  strengths. Padding: small, medium or large. Inner width: content or wide. Text turns light on dark, accent and picture
  backgrounds.
- **Cover (hero).** Full width or wide. Picture optional (without one it uses the accent colour). Overlay: light,
  medium (default) or strong. Height: medium (about 420 px), tall (about 600 px) or screen. A headline, an optional
  line, up to 2 buttons (one filled, one outlined), aligned left or centre, and a crop point (9 positions). When the
  page title is hidden (item 18) the Cover's headline is the page's main heading.
- **Columns.** 2, 3 or 4 equal columns, side by side from 768 px and stacked below. Align top or centre. An optional
  card look (light background, padding, rounded corners). Added from ready-made layouts: Picture and text (picture on
  the left or right), 3 cards, 2 columns.
- **Editor.** A Section is one row with its settings and an indented "Inside this section" list with the usual add,
  move and delete. Columns are stacked boxes ("Column 1", "Column 2"), each with its own list. Preview shows the real
  side-by-side layout. Undo and redo cover nested changes.
- **Limits.** 100 blocks per page counting nested ones; 30 in a Section; 15 in a Column.

### Data-Model.md (`SiteBlockType`)
From: PARAGRAPH, HEADING, LIST, QUOTE, IMAGE, BUTTON, SPACER, ANNOUNCEMENTS_LIST, EVENTS_LIST, SERVICE_TIMES, CONTACT.
To: adds SECTION, COLUMNS and COVER. A block's JSON gains an optional `width` (content, wide, full) and, for Section,
Columns and Cover, a list of child blocks. This needs a new migration for the enum values only (the children live in the
block's own JSON), and the block schemas stay strict: unknown fields are refused.

## 17. Site header, footer and look (Q4, Q5, Q13 to Q15)

### Product.md and Data-Model.md (`SiteSettings`)
From: "logo, one of 5 colour presets, one of 2 font presets" (item 12), header and footer unspecified.
To:
- **Header:** the church name or logo on the left, the menu on the right, and an optional call-to-action button (its
  words and the page it opens). On phones the menu folds into a button. **Footer:** church name, address, phone and
  email (from Website settings), service times, links to the pages, and a copyright line. Both are fixed designs with a
  few settings, not free-form blocks.
- **Five colour sets**, each with an accent, a dark band and a light tinted band, and text colours checked for
  readable contrast (at least 4.5 to 1): **Dawn** (default; indigo, night blue, lavender), **Meadow** (forest green,
  very dark green, pale sage), **Harbor** (ocean blue, navy, pale sky), **Clay** (terracotta, dark brown, sand),
  **Slate** (deep teal, charcoal, light grey). No free colour pickers.
- **Two font styles:** **Clean** (all sans-serif) and **Classic** (serif headlines, sans-serif body). Both use fonts
  already on the visitor's device: nothing to download, no tracking, nothing breaks if a font service is down.
- **Where it is chosen:** a new **Look** section in Website settings: colour set, font style, an optional logo (turned
  into a small WebP like any picture), and the header button. A new church starts with Dawn and Clean.

## 21. Built: step 1 of the layout blocks (widths and the Section block)

Committed and tried in the browser. A **Section** is a full-width band with a background (plain, light tint, dark, the
church colour, or a picture with a dark overlay), three spacing steps, an inner width (reading or wide) and a band
width (full or wide); its blocks are kept inside its own JSON and drawn indented in the editor ("Inside this section"),
with the usual add, move, delete, undo and redo. A **Picture** can be the reading width, wide, or the full screen. Text
blocks always stay at the reading width. Limits: 100 blocks per page in all levels, 30 in a Section, no Section inside a
Section. On the public page, light text and white buttons are used on dark, accent and picture bands, and the first
paragraph inside a Section can supply the page's search description. Migration `20261101040000_site_section_block` adds the
`SECTION` value. Still to build, in order: the Cover hero, Columns, then the header, footer and look, the "show the page
title" switch and "make this the home page".

## 22. Built: step 2 of the layout blocks (the Cover hero)

Committed and tried in the browser. A **Cover** sits on the page itself (never inside a Section), full width or wide. It has a
headline (required), an optional line of text, an optional picture (without one it uses the church colour), a picture
darkening of light, medium or strong (never off: the lightest still darkens by about a third, so white words stay readable
on a bright photo), a height of medium, tall or the whole screen, left or centre words, a crop point (9 positions), and up
to two buttons (one filled, one outline) that follow the usual link rules. A Cover's line of text can supply the page's
search description. Migration `20261101050000_site_cover_block` adds the `COVER` value. The overlay strengths for a Cover
(35, 50 and 65 per cent) are darker than for a Section picture band (25, 45 and 65), on purpose.
Also changed: the public page now sizes itself by the width of its own box (container queries), not the browser window, so
the editor's phone and tablet previews show real phone and tablet sizes. The headline is a second-level heading for now;
it becomes the page's main heading once the "show the page title" switch exists (step 4).

## 23. Built: step 3 of the layout blocks (Columns)

Committed and tried in the browser, on the real screen. **Columns** hold two, three or four equal columns, each holding up to 15
ordinary blocks. They can go on the page (content, wide or full width) or inside a Section (where they fill the band's inner
width), never inside a column; a column holds ordinary blocks only. They sit side by side from 672 px wide and stack below,
following the width of the page's own box. Options: line up at the top or in the middle, and one switch for the card look (a
light panel with padding and rounded corners, which turns translucent on dark bands). Adding offers ready-made layouts: Picture
and text (picture on the left or the right), Three cards, Two columns. In the editor each column is a stacked box ("Column 1",
"Column 2") with its own list. More columns can always be added (up to four); **fewer columns are refused while the columns that
would go still have blocks in them**, with a plain message, so nothing is lost. A ready-made layout is added only when the
whole of it fits within the 100-block page limit. Pictures, the plain-words problems and the search description all look inside
columns. Migration `20261101060000_site_columns_block` adds the `COLUMNS` value. Blocks at the top or bottom of a band or a
column no longer add their own outer space. Still to build: the header, footer and look (step 4), the "show the page title"
switch and "make this the home page".

## 24. Built: step 4 (page settings, the look, the header and the footer)

Committed and tried in the browser, on the real screens. Three parts:

- **Page settings.** A page has a **Show the page title** switch (on by default). With it off, the first Cover's headline becomes the page's one
  main heading, and the editor warns if a page with a hidden title has no Cover. **Make this the home page** (Publish permission, "Yes, I am
  sure") swaps the home address in one transaction: the old home page becomes an ordinary page with an address made from its title (the
  address the chosen page leaves behind is free for it), and the dialog says plainly when the chosen page is a draft, so the website would show
  "This page is not available" until it is published. Migration `20261101070000_site_look_and_page_title`.
- **The look.** Five colour sets (Dawn, Meadow, Harbor, Clay, Slate) and two font styles (Clean, Classic) live in one module,
  `src/features/site/look/look.ts`. A test checks that, in every colour set, the white words on the accent colour and on the dark band, the body
  and quiet text on white and on the tint, the accent colour as text, and the dark colour on a white button all meet the 4.5 to 1 contrast rule.
  Fonts are the ones already on the visitor's device. The page receives the look as CSS variables; anything not offered falls back to Dawn and Clean.
- **Header and footer.** The header has the logo (or the church name), the menu, and an optional call-to-action button, which shows only when the
  page it opens is published; on a narrow page the menu folds into a Menu button (a plain disclosure, no script). The footer is a dark band with
  the church name, address, phone and email, the service times, and a link to every page, with a copyright line. The **Look** settings are in
