# 2026-10-30: event colours

Asked for by the owner: events should be able to show in a colour on the calendar. Each entry gives the
document, the version before (From), and the version after (To), with the reason.

## 1. An event has a calendar colour

Reason: with several events in a day, colour lets the team tell kinds of event apart at a glance.

### Data-Model.md
From: `ChurchEvent` has no colour.
To: `ChurchEvent.color`, text, not null, default `DEFAULT`. It is one of a fixed set of names (`DEFAULT` (shown as
Blue), `PURPLE`, `GREEN`, `ORANGE`, `RED`, `PINK`, `TEAL`, `GRAY`) held in
`src/features/events/event-colors.ts`, and validated on create and edit. It belongs to the event, so every date of
a repeating event shares it. Not applied to the core doc yet; update it once this is accepted as permanent.

### Database (additive)
One column, `ChurchEvent.color` (migration `prisma/migrations-current/20261031000000_event_color`), applied to the
hosted database before the code, on the owner's approval. Every existing event holds `DEFAULT`, so nothing looks
different until a colour is chosen.

**What went wrong, and the rule it leaves.** The migration was first applied by hand with `prisma db execute`, which
runs the SQL but does not record it in `_prisma_migrations`. The Vercel build runs `prisma migrate deploy` against the
production database on every deploy (`scripts/vercel-build.mjs`; the local dev database is that same hosted
database). It saw the migration as pending, ran it again, and failed with "column color already exists". That failed
the first deploy of this change (`db_migration_failed`), left the previous deployment live, and left a failed row that
blocks every later deploy until it is resolved. It was recovered with
`prisma migrate resolve --applied 20261031000000_event_color`, which closed the failed row and recorded the
migration. (An earlier line in this entry wrongly said `prisma migrate status` does not read `migrations-current`;
it does, and it counts 40 migrations.) **From now on, apply migrations to the hosted database with
`prisma migrate deploy`**, as the build does. If one is ever applied by hand, run `prisma migrate resolve --applied
<name>` straight afterwards, before pushing.

### Screen
- A Color row of named swatches in the New event and Edit event forms. Each swatch has a name and a tick when
  chosen, so colour is never the only clue.
- Calendar chips use the event's colour. A cancelled date stays grey and struck through whatever its colour. An
  overlap is still flagged by the word "Overlap" before the title, so colour no longer doubles as the overlap
  warning.
- List rows and the details card show a small dot in the event's colour.

### Design tokens (needs the owner's review)
`tokens.css` gains `--event-<name>-bg`, `--event-<name>-ink` and `--event-<name>-dot` for all eight colours. The text
on every chip is at least 4.5 to 1 against its background (a test checks this). Blue is a true blue tint
(`--event-blue-*`). It first reused the pale grey panel colour, which was almost the same as the selected day's
background, so a blue chip on the selected day seemed to have no colour (fixed 2026-10-30). Every coloured chip also
has a thin outline in its own text colour, so it holds its shape on any background.

`DESIGN.md` was not changed. A categorical colour palette is a new design element, so it should go through a
grilling session before `DESIGN.md` and `tokens.css` are declared aligned.

## 2. A headcount can be recorded on any date that has happened

Reason: the headcount was only entered inside Mark done, which exists for one-time events. The dates of a repeating
event had a headcount in the data and the API, but no way to set it from the screen. `Product.md` already says events
have an optional per-occurrence headcount.

### Screen
An Attendance icon in the event card's icon row ("Record attendance", or "Edit attendance" once a number exists). It
opens a small inline form, "How many attended (Optional)". An empty box clears the number. It is available for any
date that has started and is not cancelled, repeating or not, done or not. "After the event" still appears only once
a number is recorded.

### Server
`PATCH /api/events/occurrences/{id}` refuses a headcount on a date that has not started or is cancelled (409). Clearing
a headcount is always allowed. Recording a headcount does not mark the date as "Changed".

## 3. Every API response says no-store

Reason: 63 of the 88 API routes (events, people, services, members and others) set no cache header of their own and
relied on framework defaults. Those responses are private, signed-in data, so the intent should be explicit.

### next.config.ts
From: only 25 routes said `Cache-Control: no-store` themselves.
To: a rule on `/api/:path((?!captions/live/).*)` sets `Cache-Control: no-store` on every API response. The public
captions feed (`/api/captions/live/{token}`) is the one exception: it sets its own short caching (`feedCacheControl`)
and carries caption text only.
`src/lib/api-cache-headers.test.ts` checks the rule, and fails if any other route starts choosing its own caching.

### Not changed
Data held in the browser by the data library (1 minute fresh, about 5 minutes kept, in memory per tab) is unchanged.
Pages already said `no-store`. Production was not checked; this was verified on the local dev server.

## 4. Services: newest first, ten per page, with a footer

Reason: the list grows every week and was sorted oldest first, so the newest service was at the bottom.

### Screen
- The newest service is always at the top. The sort is done on the page, so nothing else that reads
  `/api/services` changes.
- Ten services per page, with a footer in the register: "Showing 1 to 10 of 23 services" on the left, and Previous and
  Next arrows around "Page 2 of 3" on the right. The footer stays on a short list, with both arrows off.
- "Select all" covers the rows on the current page only, so a bulk delete never reaches rows the person has not seen.
  Changing a filter goes back to page 1.
- The arrows are quiet icon controls (no border, no fill, muted until hovered, 44px) with a name and tooltip.

### Code
`src/lib/list-pagination.ts` (`paginate`, `latestFirst`, `PAGE_SIZE = 10`, tested) and
`src/components/ui/list-pagination-footer.tsx`, built on `src/components/ui/pagination.tsx`, which is shadcn's
pagination adapted to this app (real buttons, and its light-surface colours, because shadcn's outline button filled
with the dark app background). Events uses the same footer on its list.

## 5. The Events screen now follows the register layout

Reason: Events had its own look. It now follows the page contract in `DESIGN.md` (header, one register with a toolbar,
a footer) like the other list pages, and the owner personalised the details.

### Layout
- Header with `ui-page-header` and the primary New event button. One register surface with a toolbar: the month, the
  previous and next icons, Today, the Month and List switch, and a refresh icon. The count beside the switch was
  removed.
- The details of an event are a separate card beside the calendar, with an X to close it. The calendar goes full
  width whenever the card is closed (the width glides). The card opens when an event, or a day that has events, is
  chosen, or New event is pressed. List view and the past events review list use the same card on a wide screen. On
  a phone the details open under their row, with the purple rule, as Services rows do.
- List and review views have the pagination footer, ten per page, in date order.
- Loading: a calendar-shaped skeleton, shown for the new month while it loads instead of the old month's events
  (the old month is kept underneath only so the page's buttons keep working). Months already loaded appear at once.
- Errors: a red band with Retry, for the month and for the review list. The review list loads on its own after Review
  is pressed; it used to show "Nothing to review" while it loaded, and forever if it failed.
- Past Events to Review: Title Case heading, no count, and a left-arrow icon (named "Back to calendar") instead of a
  labelled button.

### The details card
- The actions are quiet icon buttons under the event's details (no border, no fill, muted, red on hover for the
  destructive ones): Edit, Attendance, Cancel, Announce, Restore, Mark done, Mark not done, Delete. Each has a name
  and a tooltip. One Cancel icon replaces two: with two choices it opens a small menu (Cancel this date, Cancel all
  dates); with one choice it opens that confirmation.
- Cancel this date, Cancel all dates and Delete ask in a modal ("Yes, I am sure"), not inside the card. The icons stay
  on the card behind the modal. Edit and Mark done open inside the card.
- Registration and After the event are shown only when they have something in them. Status shows as a coloured dot and
  a word. Filler lines were removed ("Only the title, date, time and place are shown.", "To delete this event, cancel
  it first.", "Dates are added automatically about four months ahead.", and the explainer in Edit).
- The Repeat choices read Never, Daily and Weekly. Optional labels read "(Optional)" where touched.
- Fields use the shared People field styles. The website switch has no border.

### Motion
The details card slides and fades in and out, the calendar or list glides to its new width, the card content fades
when it changes, the month fades in, list rows fade in one after another, and Edit and Mark done fold open and shut
(the card used to snap shut). Everything follows the system's reduced-motion setting.

## 6. One date picker and one time picker across the app

Reason: the browser's own date and time fields looked different from the Services date picker and from each other.

### Date
Every date field now uses the Services date picker (`ProductionDatePicker`): Events (create and edit), Announcements
(both optional dates, with Clear), and three fields in the service builder. The picker gained a `minValue`, so an end
date cannot be chosen before its start.

### Time
A new `ProductionTimePicker`: an alarm-style popup with three wheels (hour, minute, AM or PM) that scroll up and down
under a highlighted band. It works with a touch scroll, a mouse wheel, a mouse drag, a tap on a row, and the arrow
keys, and keeps the same 24-hour "HH:mm" value the forms always held. Used for Start and End in Events.
`src/lib/time-of-day.ts` holds the tested maths. A test fails if a browser date or time input comes back anywhere.

## 7. Fixes found while checking in the browser

- "Announce this event" opened Announcements with nothing selected after a client navigation: the screen read
  `window.location`, which still has the old address while the new page first renders. It now reads the router.
- Changing the date of a new event now moves the preselected weekday with it, and never undoes a choice made by hand.
- A cancelled date no longer offers "Announce this event".
- The Events screen is tested in an Edge window that Playwright opens (`--browser msedge` in the user's global MCP
  settings), because Opera GX cannot be driven from it.

## 8. Decisions for the owner (nothing here was applied to `DESIGN.md`)

`DESIGN.md` changes go through a grilling session first, so these are recorded as proposals:
1. **Register footer.** `DESIGN.md` does not describe the footer, the pagination control or the quiet icon arrows.
2. **Icon-only actions.** `DESIGN.md` says icons support words and do not replace them. The owner asked for icon-only
   actions in the event card, each with a name and tooltip.
3. **"Keep it".** Serious confirmations read "Yes, I am sure" as `DESIGN.md` says, but the way out reads "Keep it", in
   plain text with no fill, instead of "Cancel", because "Cancel" next to "Cancel this date?" is confusing.
4. **Categorical colours** (item 1) and the **alarm-style time picker** (item 6) are new design elements.
5. **Overlap.** An overlapping event keeps its own colour and is flagged only by the word "Overlap" before its title.
   It used to turn amber.
