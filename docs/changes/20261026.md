# 2026-10-26: public site, no congregant login, free-plan facts

Changes to the baseline written earlier the same day. Each entry gives the
document, the version before (From), and the version after (To), with the reason.

## 1. Congregants do not log in (supersedes self-profile and Person-User link)

Reason: much of the congregation is elderly and not tech-savvy. The tech team
manages all member data, so a member login has no job.

### Access-and-Privacy.md
From:
- "Self-access: a user linked to a Person can always view their own profile,
  without any PEOPLE grant", plus "Linking a user to a person" (admin link or
  invitation carrying a `personId`, no self-claim).
To:
- Removed both sections. Accounts (`User`) are tech-team accounts only. Owner and
  Admin have full access; a Member sees only what their grants allow.

### Data-Model.md
From: "Person-User link: optional, one Person to at most one User per workspace".
To: Removed. `Person` has no link to `User` in the first cut. Invitations no
longer carry a `personId`.

### Roadmap.md
From: step 2 "PEOPLE permission module and the self-profile rule".
To: step 2 is the PEOPLE permission module only.

### Product.md
From: "A linked member can always see their own profile", and "nothing that
requires attendees themselves to use the app".
To: Congregants do not log in; they see only the public church site.

## 2. Public church site with a page builder

Reason: each church wants a public web presence, WordPress-like, showing
announcements, events, posts and pages. Anyone with the URL can view it.

### Product.md
From: modules People, Ministries, Events, Announcements, Worship, Dashboard,
Settings.
To: adds **Site**, a block-based page builder with posts. Blocks include rich
text, image, button, announcements list, events list, service times, contact.
No custom HTML, CSS or JavaScript, and no themes beyond a logo and a color and
font preset. Custom domains and a free-form builder are deferred.

### Architecture.md
From: public routes were login, auth callback and `/captions/live/{id}` only.
To: adds the public site at `/c/{workspaceSlug}` (no login) beside the app at
`/w/{workspaceSlug}`. Public pages are cached and pre-rendered and any public
endpoint is rate limited. Read this Next.js version's caching docs first.

### Data-Model.md
From: no site models.
To: adds `SiteSettings` (per workspace, including `indexable`, default false),
`Page`, `PageBlock` (ordered, typed), and `Post`. Adds `isPublic` to
`ChurchEvent` and `Announcement`. Public routes read only public-safe fields.

### Access-and-Privacy.md
From: no public surface.
To: opt-in per item. Nothing is public unless marked public. `Person`,
ministry membership, birthdates, baptism and attendance never appear on the
public site, and no public route may query those tables (needs a test).
`noindex` is a request to crawlers, not access control.

### Roadmap.md
From: ten steps ending with `AGENTS.md` and `README.md` rewrite.
To: adds the site/page builder after Announcements as the first public feature,
named as the step most likely to slip. Dashboard, Worship regrouping and tool
refinements shift one step later.

## 3. Site visibility: unlisted by default

From: not decided.
To: each church has a switch, `indexable`. Default off: `noindex`, not in a
sitemap. On: indexable. Settings holds the switch.

## 4. Keep-alive job and hosting plans

Reason: Supabase pauses Free projects after about 7 days of low activity.

### Architecture.md
From: "Assumed free-plan limits (verify on the Supabase dashboard): about 1 GB
total, 50 MB per file, project pauses after about a week."
To: verified against Supabase and Vercel docs on 2026-10-26. Supabase Free:
500 MB database, 1 GB file storage, 5 GB egress, 50 MB file cap that cannot be
raised, two free projects, paused after low activity over 7 days (restorable
within 1 year). Vercel Hobby cron: 100 jobs, once per day, +/-59 min precision.
Adds a daily keep-alive: a Vercel Cron call to a protected internal route (same
secret pattern as `formatter-cleanup`) that makes one small database write.
Whether a read would also count is unconfirmed, so the job writes.
Vercel Hobby is non-commercial personal use only: move to Pro before charging
churches or if anyone is paid for the work. Check Vercel's terms against the
actual situation.

## 6. Design direction: the hand-built approach is the contract

Reason: the three mockup sets depict the old production product and cover no
CMS screen. The approach already built into Services, Teams, the Song Formatter,
and Settings is what the owner wants for new screens.

### DESIGN.md
From: interim; derived from the Stitch project; direction "pending" among three
mockup sets.
To: a contract written from the code: page header, one register with a fixed
toolbar order, ledger rows with a trailing menu, purple as a signal, section
Save and inline editing in Settings. Settings has no page header on purpose.
New screens use `ui-btn-danger` (red at rest), a three-dot 44px row menu,
`ui-modal-close` with an explicit Cancel, one 1200px breakpoint, and toasts for
every mutation. No text under 12px; sentence-case labels; uppercase mono only
for small codes; visible words on primary actions; red reserved for errors;
WCAG 2.2 AA required. The dark rail stays. Old pages are fixed only when touched.

### Roadmap.md
From: step 5 "pick the design direction, then write Design.md".
To: step 5 is the design contract, done today. The public-site template is
designed in step 8.

### AGENTS.md, README.md

To: DESIGN.md described as the visual contract.

## 12. Step 3 decisions: names, one step, destructive drop held

### Data-Model.md
From: `Person.name` as one field; step 3 split into 3a and 3b.
To: `firstName` and `lastName`, both required (people with the same name must be

### Roadmap.md
From: step 3 as screens plus a later switch.
To: step 3 built in eight ordered pieces, one commit each.

### Decided with the owner (screen design)
People list: Name, Ministries, Status, Birthday, Baptism; filters Status and
Ministry; Archived hidden by default. Person dialog: first name, last name,
status, gender, birthdate as month/day/year selects, ministries as a checklist,
baptism status with a date enabled only when Baptized, and a "why we collect this"
note on the page. Row menu: Edit, Archive or Restore, and Delete permanently
(Owner and Admin only, with a confirmation). Bulk: Add to ministry, Archive. Every
save records created-by and last-edited-by, shown in the dialog. Ministries screen:
Ministry, Leader, Members, Active; a ministry is archived, never deleted. Export of
a person's data and a deletion log are deferred. The nav replaces Teams with People
and Ministries; the wider rail restructure waits for the Worship regrouping step.

## 13. Step 3 progress

Built, one commit each, tests first: schema (migration
`20261026020000_person_names_and_service_ministry`, applied to hosted; all 9
services now point at a Ministry), the People API, the Ministries API, and the People
and Ministries screens with nav entries. Verified by driving the real app: add a
person with a ministry, archive (hidden from the default list), find them under the
Archived filter, delete permanently, and open the Ministries list and dialog. The
test person was removed; hosted holds 0 people and 16 Ministries.

Lessons recorded: dropping a column drops its index, so an explicit DROP INDEX must
use IF EXISTS (the first apply of the names migration failed on this, rolled back
cleanly, and was re-applied after `prisma migrate resolve --rolled-back`). A route
file may export only HTTP handlers, so shared helpers live in feature modules.
Saves wait for the lists to reload, so no stale empty state shows after adding.
